# 高级配置

本文说明令牌生命周期、签名证书、HTTPS、客户端安全策略和当前协议边界。先完成 [05-配置 OAuth 客户端](./05-配置OAuth客户端.md) 的基础配置，再按部署环境选择本页设置。

## 1. Provider 基础配置

`src/NexusAuth.Host/appsettings.json` 中的关键配置如下。生产环境建议通过环境变量或 Secret 注入，不要把密码写进仓库：

```json
{
  "Jwt": {
    "Issuer": "https://sso.example.com",
    "DefaultAudience": "NexusAuth",
    "SigningMode": "Certificate",
    "SigningCertificatePath": "/run/secrets/nexusauth-signing.pfx",
    "SigningCertificatePassword": "从 Secret 注入",
    "AccessTokenLifetimeMinutes": 60,
    "DeviceCodeLifetimeMinutes": 15,
    "RefreshTokenLifetimeMinutes": 43200
  }
}
```

对应的环境变量示例：

```bash
NEXUSAUTH_JWT_ISSUER=https://sso.example.com
NEXUSAUTH_JWT_SIGNING_MODE=Certificate
NEXUSAUTH_JWT_SIGNING_CERTIFICATE_PATH=/run/secrets/nexusauth-signing.pfx
NEXUSAUTH_JWT_SIGNING_CERTIFICATE_PASSWORD=REPLACE_FROM_SECRET
NEXUSAUTH_JWT_ACCESS_TOKEN_LIFETIME_MINUTES=60
NEXUSAUTH_JWT_REFRESH_TOKEN_LIFETIME_MINUTES=43200
```

`Issuer` 必须与发现文档、令牌中的 `iss` 和客户端配置使用的 Provider 地址一致。修改 Issuer 后，已有客户端的回调和反向代理配置也要同步检查。

## 2. X.509 签名证书

### Development

Docker Compose 默认以 `Development` 运行。缺少开发证书时，Provider 会生成自签名 PFX 并写入 `nexusauth-signing-key` 数据卷，重启后继续使用同一把密钥。可以通过以下变量设置开发 PFX 密码：

```bash
NEXUSAUTH_SSO_ENVIRONMENT=Development
NEXUSAUTH_JWT_DEVELOPMENT_SIGNING_CERTIFICATE_PASSWORD=REPLACE_WITH_DEV_PASSWORD
```

开发证书只用于本地测试，不应作为生产证书复制。

### Production

生产环境必须显式提供由证书管理系统、Vault、KMS 或 Kubernetes Secret 管理的 PFX：

```bash
NEXUSAUTH_SSO_ENVIRONMENT=Production
NEXUSAUTH_JWT_SIGNING_MODE=Certificate
NEXUSAUTH_JWT_SIGNING_CERTIFICATE_PATH=/run/secrets/nexusauth-signing.pfx
NEXUSAUTH_JWT_SIGNING_CERTIFICATE_PASSWORD=REPLACE_FROM_SECRET
```

Provider 不会在生产环境自动生成证书。路径不存在、PFX 密码错误、证书无私钥或证书不可用于签名时，应让部署失败并修复配置，不要退回开发密钥。

当前还保留兼容模式：

```bash
NEXUSAUTH_JWT_SIGNING_MODE=RsaKeyFile
NEXUSAUTH_JWT_SIGNING_KEY_PATH=/run/secrets/signing-key.json
```

生产环境的 `RsaKeyFile` 也必须预置密钥文件，不会自动生成。新部署优先使用 X.509 PFX，并规划证书轮换和 JWKS 缓存刷新策略。

## 3. 令牌生命周期和滑动续期

- `AccessTokenLifetimeMinutes` 控制 access token 的有效期。短生命周期可以缩小泄露窗口。
- `RefreshTokenLifetimeMinutes` 控制 refresh token 的绝对有效期；它不是 access token 的 Cookie 有效期。
- 只有请求 `offline_access` 且客户端允许 `refresh_token` 时才签发 refresh token。
- refresh token 使用后会轮换，客户端必须保存新 token 并丢弃旧 token。
- Workbench BFF 使用服务端加密 Cookie 保存令牌，并在 access token 临近过期时刷新；刷新失败则要求用户重新登录。

建议生产环境的 access token 保持较短，refresh token 的生命周期根据业务风险决定。不要为了延长浏览器会话而把 access token 设成多年有效；应使用受保护的 BFF 会话和 refresh token。

## 4. 授权端点策略

### RequirePkce

`require_pkce` 是客户端级别策略，不是全局忽略的开关：

- `true`：授权请求必须提供 `code_challenge` 和 `S256`；换 token 必须验证 `code_verifier`。
- `false`：允许可信机密后端在没有 challenge 时使用授权码，但如果请求主动携带 S256 challenge，仍然会验证它。
- `plain` 和未知 `code_challenge_method` 永远不会被接受。

生产 Web/BFF 应保持 `true`。关闭它只适用于明确知道风险、且凭据不会暴露给终端用户的旧式机密后端。

### response_mode

授权端点支持：

- `query`：默认或显式指定时，成功响应和可安全回跳的错误通过查询参数返回。
- `form_post`：使用 HTML 表单 POST 到已登记的回调地址，适合不希望把响应放入 URL 的 OIDC 客户端。

授权错误的处理遵循安全优先原则：Provider 只有在客户端存在且 `redirect_uri` 精确匹配后才会回传错误；错误中会包含 `error`、可选的 `error_description` 和原始 `state`。未知 `response_mode` 会按默认 `query` 向已验证的回调地址返回 `invalid_request`，不会执行未知模式。如果回调地址未知、未登记或无法确认安全，Provider 直接返回本地 400 响应，不把任何错误发到请求中的地址。

## 5. 客户端认证策略

客户端登记一个 `token_endpoint_auth_method`，每次请求只能使用对应的认证来源：

| 方法 | 请求形式 | 算法/要求 |
|------|----------|-----------|
| `client_secret_basic` | `Authorization: Basic base64(client_id:client_secret)` | 服务端 Web/BFF 推荐。 |
| `client_secret_post` | 表单 `client_id` + `client_secret` | 仅为兼容需要时使用。 |
| `client_secret_jwt` | `client_assertion_type` + `client_assertion` | `HS256`，使用已登记共享密钥，必须有短时效 `exp` 和唯一 `jti`。 |
| `private_key_jwt` | `client_assertion_type` + `client_assertion` | `RS256`，使用客户端私钥签名，Provider 使用已登记内嵌 JWKS 验签。 |

Basic 头、表单 secret、JWT assertion 混用，或者同一请求中出现互相矛盾的 `client_id`，都会拒绝，不会回退到另一个认证方式。认证失败的 HTTP 语义为：

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="NexusAuth"
Content-Type: application/json

{"error":"invalid_client","error_description":"..."}
```

具体 `error_description` 只用于排错，不应依赖其文字内容做程序分支。客户端应根据 `error` 和 HTTP 状态处理。

## 6. HTTPS、代理和 Cookie

生产环境必须使用 HTTPS，并配置反向代理的可信转发头。推荐检查：

1. Provider 的 `Issuer` 使用公网 HTTPS 地址。
2. 反向代理只信任明确的代理网段，正确传递 `X-Forwarded-Proto` 和 `X-Forwarded-Host`。
3. 所有回调 URI 使用 HTTPS，避免把生产 token 回传到 HTTP。
4. Workbench 的认证 Cookie 设置 `Secure`、`HttpOnly`，并根据跨站登录流程选择合适的 `SameSite`。
5. BFF 的跨站写接口增加 CSRF token 或严格的 Origin/Referer 检查。
6. `AllowedHosts` 不要在生产环境保持 `*`，应列出真实 Host。

本地 HTTP 只用于开发。`RequireHttpsMetadata=false` 只能出现在本地或隔离的 Compose 环境，生产应设为 `true`。

## 7. 轻量级可配置登录流程

`NexusAuth.Host` 支持按顺序执行密码和 TOTP 两个登录步骤。配置位于 `LoginFlow` 和 `Totp` 节，生产环境建议通过环境变量或 Secret 注入：

```json
{
  "LoginFlow": {
    "PendingStateLifetimeMinutes": 5,
    "SessionLifetimeMinutes": 1440,
    "RememberMeLifetimeDays": 3,
    "AllowRememberMe": true,
    "Steps": [
      { "Type": "password", "Requirement": "required" },
      { "Type": "totp", "Requirement": "conditional" }
    ]
  },
  "Totp": {
    "Issuer": "NexusAuth",
    "EnrollmentLifetimeMinutes": 10
  }
}
```

Compose 和直接运行 Provider 都使用同一个单下划线环境变量覆盖该值：

```bash
NEXUSAUTH_LOGIN_FLOW_REMEMBER_ME_LIFETIME_DAYS=3
```

未设置时默认 `3`。可设范围为 `1`–`30`，设置为范围外值会使 Host 在启动校验时失败；修改后需要重启 Provider。勾选登录页的“几天内免登录”后，持久 Cookie 与服务端 SSO 会话会在该固定期限同时过期，不会因用户持续访问而滑动续期。

### LoginFlow 字段

| 字段 | 说明和约束 |
|------|------------|
| `PendingStateLifetimeMinutes` | 密码通过后、等待 TOTP 验证的受保护中间状态有效期，范围为 1–15 分钟。过期后必须重新输入密码。 |
| `SessionLifetimeMinutes` | 最终 SSO 登录会话有效期，范围为 5–1440 分钟。 |
| `RememberMeLifetimeDays` | 勾选“几天内免登录”时持久 SSO Cookie 和服务端 SSO 会话的绝对有效期，默认 3 天，范围为 1–30 天。使用 `NEXUSAUTH_LOGIN_FLOW_REMEMBER_ME_LIFETIME_DAYS` 覆盖。该 Cookie 不会滑动续期，期限从成功登录时开始计算。 |
| `AllowRememberMe` | 是否显示并接受登录页的“几天内免登录”。设为 `false` 时，即使请求提交该值也不会创建持久会话。未勾选时使用 `SessionLifetimeMinutes`，并保留滑动续期。 |
| `Steps` | 有序步骤列表，只支持 `password` 和 `totp`。必须恰好包含一个排在第一位的 `password` 步骤，且其 `Requirement` 必须为 `required`；每种类型最多出现一次。 |

`Steps` 中的 `Requirement` 仅支持以下组合：

| 步骤 | `conditional` | `required` |
|------|--------------|------------|
| `password` | 不支持 | 必须输入正确密码；该步骤必须排在第一位。 |
| `totp` | 已绑定并启用身份验证器的用户需要输入六位动态验证码，未绑定用户可继续登录。 | 所有用户都必须先完成 TOTP 绑定；未绑定用户会被拒绝登录，已绑定用户还必须输入正确验证码。 |

不配置 `totp` 时，登录流程只有密码步骤。`Steps` 为空时使用默认流程：`password/required` 后接 `totp/conditional`。配置校验失败会阻止 Host 启动，因此修改配置后应检查启动日志。

`Totp.Issuer` 是身份验证器中的服务名称和二维码标签，默认值为 `NexusAuth`；`EnrollmentLifetimeMinutes` 是 `/account/two-factor` 发起绑定后待确认密钥的有效期，范围为 1–30 分钟。TOTP 凭据保存在 `user_credentials`，一个用户可绑定多个独立设备；每个设备各自保存受保护密钥和动态码防重放计数。绑定和停用 TOTP 都要求当前密码；停用任一设备后会撤销该用户的现有 SSO 会话。

### 推荐上线顺序

切换到强制 TOTP 前，必须先让用户完成绑定。推荐按以下顺序发布：

1. 使用全新的 PostgreSQL 数据卷初始化。`production-init.sql` 是唯一的数据库结构来源，直接创建可一对多扩展的 `user_credentials` 表；不要在已存在的数据卷上混用旧版本结构。
2. 确认所有 Host 实例使用同一份持久化、共享的 Data Protection key ring，再开始用户绑定。TOTP 密钥以 Data Protection 密文存储，密钥环丢失或不一致会导致已绑定密钥无法解密。
3. 保持 `totp/conditional` 运行，让用户在 `/account/two-factor` 绑定并确认身份验证器，观察登录审计和失败情况。
4. 确认目标用户已完成绑定后，将 `Steps` 中的 TOTP 修改为 `"Requirement": "required"`，再滚动重启所有 Host 实例。
5. 若仍有未绑定用户，先恢复为 `conditional`，完成补绑后再重试；不要直接在生产环境启用 `required`。

`required` 的行为是“未绑定用户不能登录”，不是“登录后再提示绑定”。如果在用户完成绑定前启用它，所有未绑定用户（包括管理员）都会被锁在登录页之外；应预先保留可审计的运维恢复路径。

## 8. Data Protection 和多副本

Workbench Cookie 和 `NexusAuth.Host` 的登录流程都使用 ASP.NET Core Data Protection。Host 还使用它保护密码通过后等待 TOTP 的中间状态，以及数据库中的 TOTP 密钥密文。多副本部署时必须让同一应用的所有实例共享：

- Data Protection key ring；
- 认证 Cookie 名称和 scheme；
- Provider 数据库以及 refresh token 状态。

Host 的 key ring 必须持久化，并由所有 Host 副本以相同权限读取。某个副本使用临时或独立的 key ring 时，跨副本提交的 TOTP 中间状态会失效，更严重的是该副本无法解密已绑定用户的 TOTP 密钥，登录会持续失败。轮换密钥时应保留旧密钥可解密的时间窗口；不要删除仍在使用的旧 key ring。

Docker Compose 已通过命名卷保存 Provider 和 Workbench 的 Data Protection keys。Kubernetes 或云环境应使用持久化卷、对象存储或受保护的密钥存储，并限制读取权限。清空 key ring 会让现有登录 Cookie 失效，这是可接受的紧急撤销手段，但要配合用户重新登录通知。

## 9. 发现文档与能力边界

接入方应读取 `/.well-known/openid-configuration`，不要猜测 endpoint。当前发现文档重点包含授权码、client credentials、refresh token、device code、PKCE S256 和四种客户端认证方式。

以下能力当前未实现，不要仅凭其他产品的文档或名称假设 NexusAuth 支持：

| 扩展 | 当前状态 | 说明 |
|------|----------|------|
| PAR | 未实现 | 没有 `/request` 推送授权请求端点。 |
| JAR | 未实现 | 不接受签名的 `request` JWT 作为授权请求。 |
| JARM | 未实现 | 授权响应不是 JWT response。 |
| DPoP | 未实现 | access token 不是 DPoP 绑定令牌。 |
| mTLS | 未实现 | 不按客户端证书认证或绑定 token。 |
| 动态客户端注册 | 未实现 | 客户端必须通过 Workbench/数据库登记。 |
| `none` public client | 未实现 | 当前 token endpoint 需要登记的机密客户端认证。 |
| CIBA | 未实现 | 没有 backchannel authentication 流程。 |

需要这些扩展时，应先单独进行威胁建模、发现文档和兼容性设计，不能通过放宽现有参数校验临时模拟。

## 10. 监控和审计

生产至少记录以下事件的时间、客户端、用户和结果：登录成功/失败、授权拒绝、授权码签发和消费、refresh token 轮换、撤销、客户端凭据变更和证书加载失败。

日志中不要记录：

- access token、refresh token、authorization code；
- `client_secret`、private key、完整 client assertion；
- 登录密码和完整 Cookie。

对 token、device authorization 和登录接口设置限流，并通过健康检查监控数据库、签名证书和关键依赖。安全相关事件应能关联 trace/correlation ID，但不能通过 ID 反推出令牌原文。

更多验证顺序和错误决策见 [11-OAuth/OIDC 协议设计](./11-OAuth-OIDC协议设计.md)。
