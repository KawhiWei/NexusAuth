# 常见问题

本文按当前 NexusAuth Provider、Workbench 和 Demo 的实际实现整理。排障前先确认组件地址：Provider 默认 `http://localhost:5100`，Workbench API 默认 `http://localhost:5051`，Workbench Dashboard 默认 `http://localhost:5273`。

## 登录与会话

### 登录后刷新页面又回到登录页

先区分应用类型：

- Workbench Dashboard 通过同源的 `/api/auth/me` 检查 Workbench API 的 HttpOnly Cookie。前端调用的 `'/auth/me'` 会由 Axios `baseURL: '/api'` 拼成 `/api/auth/me`。
- Demo Web 通过 Vite `/api` 代理调用对应 BFF 的 `/api/auth/me`，不会调用 Provider 的 `/auth/me`；Provider 没有这个接口。

然后检查：

1. 浏览器是否保存了对应域名的 Cookie，请求是否携带 `withCredentials`。
2. Dashboard 的 `/api` 是否代理到 `localhost:5051`；Demo 是否代理到 `5201` 或 `5301`。
3. BFF/Workbench 的 ASP.NET Core Data Protection key 是否持久化；多副本必须共享同一组 key ring。
4. Provider、客户端 `redirect_uri`、Issuer 和反向代理的 Host/协议是否一致。
5. BFF 的 refresh token 是否已经过期、轮换后是否仍在使用旧值。

### “几天内免登录”如何配置？

Provider 登录页的“几天内免登录”由以下环境变量配置：

```bash
NEXUSAUTH_LOGIN_FLOW_REMEMBER_ME_LIFETIME_DAYS=3
```

未设置时默认 `3` 天，允许范围为 `1` 到 `30` 天。修改后必须重启 Provider；已经签发的 Cookie 和服务端 SSO session 不会被新配置延长。勾选后，浏览器持久 Cookie 与 `sso_sessions` 中的服务端会话从成功登录时开始按固定期限过期，不会因持续访问而滑动续期。

该变量只影响 Provider 的浏览器 SSO 会话，不等于 access token 或 refresh token 的生命周期，也不会自动改变 Workbench 的 24 小时会话或 Demo BFF 的开发 Cookie。

### 没有勾选免登录时，会话多久失效？

未勾选时使用 `LoginFlow:SessionLifetimeMinutes`，默认 `1440` 分钟，Provider Cookie 保持滑动续期。其他登录流程字段可在 `src/NexusAuth.Host/appsettings.json` 或标准 .NET 配置源中设置。

### `redirect_uri` 不匹配

常见响应是：

```json
{"error":"invalid_request"}
```

`redirect_uri` 必须与客户端登记值逐字符匹配，包括协议、Host、端口、路径、大小写、末尾 `/` 和登记值中的查询字符串。未知/停用客户端或回调地址不匹配时，Provider 不会向请求中的地址回跳，而是返回本地错误页面或 HTTP 错误。

不要使用通配符回调地址，也不要把 `invalid_request_redirect_uri` 当作当前实现的错误码。

### PKCE 验证失败

Provider 只接受 `code_challenge_method=S256`。授权码兑换时 verifier 缺失、被篡改或计算不一致通常返回：

```json
{"error":"invalid_grant"}
```

客户端应为每次授权生成一次性 `code_verifier`，并按下式发送 challenge：

```text
code_challenge = BASE64URL(SHA-256(ASCII(code_verifier)))
```

兑换授权码时发送同一个 verifier。`state` 不能代替 PKCE，PKCE 不能代替 `state`；OIDC 请求还应保存并校验 `nonce`。当前实现不接受 `plain`，不要依赖 `invalid_code_verifier` 这个非标准错误码。

### `invalid_client`

Token、introspection、revocation 和 device authorization 等需要客户端身份的端点，认证失败返回 HTTP `401`、OAuth 错误 `invalid_client`，并带：

```http
WWW-Authenticate: Basic realm="NexusAuth"
```

检查：

1. `client_id` 是否存在且已启用；
2. 请求认证方式是否与 `token_endpoint_auth_method` 一致；
3. `client_secret_basic` 的 Basic 值是否是正确的 `client_id:client_secret`；
4. `client_secret_jwt` 是否使用 HS256，`private_key_jwt` 是否使用 RS256，issuer、subject、audience、exp、jti 和密钥是否正确；
5. 是否同时发送 Basic、表单 secret 或 JWT assertion。认证来源冲突会直接拒绝，不会静默回退。

当前支持 `client_secret_basic`、`client_secret_post`、`client_secret_jwt` 和 `private_key_jwt`；public client 的 `none` 未实现。

## 前端与 BFF

### Dashboard 登录页死循环或反复跳转

Dashboard 的 Axios 拦截器仅在非 `/auth/` 请求收到 401 时跳转 `/login`，以免把登录检查本身再次拦截。检查：

- `src/api/request.ts` 的 `baseURL` 是 `/api`，且 `withCredentials` 为 `true`；
- `/api/auth/me`、`/api/auth/login` 和 `/api/auth/logout` 不触发全局跳转；
- Provider 登记的回调是 `http://localhost:5051/signin-oidc`（生产替换为 HTTPS API 地址）；
- 登出响应的 `logoutUrl` 非空时，前端跳 Provider 的 `/connect/endsession`。

Demo 前端的请求封装只返回 HTTP 状态，没有 Dashboard 同款的全局 401 跳转；Demo 应在页面层处理未登录状态。

### TypeScript 类型检查命令不存在

本仓库没有 `npm run typecheck` 脚本。Dashboard 的 `npm run build` 已包含 `tsc -b`：

```bash
npm --prefix admin/src/NexusAuth.Workbench.Dashboard run build
npm --prefix admin/src/NexusAuth.Workbench.Dashboard run lint
```

Demo 前端可分别执行：

```bash
npm --prefix demo/src/Demo.Web run build
npm --prefix demo/src/Demo.Web.ClientSecret run build
```

### 跨域请求报 CORS 错误

当前仓库没有通用的 `services.AddCors` 示例。默认部署是浏览器访问 Dashboard 或 Demo 的同源地址，再由 Vite/Nginx 将 `/api` 代理到 BFF，因此 Cookie 不需要跨站发送。

如果必须使用独立前端域名，应在代理或 BFF 边界显式配置允许的 Origin、方法、请求头和凭据，并同步检查 Cookie 的 `SameSite`、`Secure` 和 CSRF 防护。不要用 `AllowAnyOrigin` 与 `AllowCredentials` 的组合掩盖配置问题。

### 登出后仍能调用接口

登出包含三层状态：

1. Demo BFF 的 `POST /api/auth/logout` 尝试撤销 access token 和 refresh token，清除 BFF Cookie，并返回 Provider 登出地址。
2. Workbench API 的 `POST /api/auth/logout` 清除 `.NexusAuth.Workbench` Cookie；启用 `SignOutProvider` 且有 ID Token 时返回 `/connect/endsession` 地址。
3. Provider 的 `/connect/endsession` 校验 `id_token_hint` 和已登记的 `post_logout_redirect_uri`，撤销用户 token/session 并清除 Provider Cookie。

只清浏览器 Cookie 而不跳 Provider，其他客户端仍可能复用 Provider 会话；只撤销 access token 而保留 refresh token，BFF 可能再次刷新。

### Token 刷新失败

当前默认 Provider 生命周期是 access token `60` 分钟、refresh token `43200` 分钟（30 天）。refresh token 使用后会原子轮换旧 token，客户端必须保存新 token，不能继续重用旧值。

Workbench 在 access token 距过期不超过 1 分钟时自动 refresh 并续新的 24 小时会话；Demo BFF 也会在 Cookie 验证时按自身策略 refresh。refresh token 失效、客户端不匹配、用户停用或 Provider 不可达时，BFF 会拒绝会话，前端应重新登录。

## Provider、数据库与部署

### 接口返回 429

Provider 按来源 IP 和端点族使用每分钟补充的 token bucket，队列长度为 0：

| 端点族 | 每个来源 IP/分钟 |
|---|---:|
| `/account/login` | 10 |
| `/connect/token` | 60 |
| `/connect/deviceauthorization` | 20 |
| `/connect/introspect` | 120 |
| `/connect/revocation` | 60 |
| `/device` | 30 |

超限返回 HTTP `429`、`error=too_many_requests` 和 `Retry-After: 60`。设备客户端还应遵循 token 响应中的 `interval`，收到 `slow_down` 后增加轮询间隔。

### 数据库连接失败

检查 PostgreSQL 是否运行、连接串是否包含正确的 Host/端口/用户名/密码和 `Search Path=nexusauth`，以及 `nexusauth` 中是否执行了当前版本的 `production-init.sql`。Compose 的 Provider 和 Workbench 必须使用同一个数据库卷与连接配置。

`production-init.sql` 不创建数据库或角色，只负责全新 `nexusauth` 数据库的最终 schema；数据库和角色由部署或 DBA 流程创建。数据库用户还需要能够使用 `pgcrypto` 扩展。

### 空库初始化时报 `relation already exists`

`production-init.sql` 不是 EF Core migration，也不是已有数据库的升级脚本；当前仓库没有用于升级历史 schema 的 EF Core migrations。先备份数据，由 DBA 创建新的空数据库后执行：

```bash
psql -U nexusauth -d nexusauth -v ON_ERROR_STOP=1 -f production-init.sql
psql -U nexusauth -d nexusauth -v ON_ERROR_STOP=1 <<'SQL'
SET search_path TO nexusauth;
\i admin/src/NexusAuth.Workbench.Api/seed.sql
SQL
```

`demo/seed.sql` 仅供本地演示，不能在生产执行。

### Docker 重启后数据或配置没有变化

PostgreSQL 官方镜像只在新的数据卷首次初始化时执行 `/docker-entrypoint-initdb.d` 下的脚本。查看状态和日志：

```bash
docker compose ps
docker compose logs --tail=200 db
docker compose logs --tail=200 sso
docker compose logs --tail=200 admin-api
```

只有确认本地数据可以全部删除时，才执行：

```bash
docker compose down -v
docker compose up --build
```

`down -v` 会删除 Compose 管理的 PostgreSQL、签名密钥和 Data Protection 数据卷；生产环境不要用它代替迁移或恢复流程。

### Docker 容器无法启动

按依赖顺序检查 `db` healthcheck、SSO 数据库和签名配置、Workbench 的 `Authority`/`BackchannelAuthority`/客户端密钥/回调地址、宿主机端口 `5100`/`5051`/`5273`，以及 Nginx 是否把 `/api` 转发到 `admin-api:8080` 并保留 Cookie 和 `X-Forwarded-*`。

### 生产 HTTPS 配置

生产使用公网 HTTPS Issuer、受管 X.509 PFX、`RequireHttpsMetadata=true` 和明确的 `AllowedHosts`。反向代理应传递 `X-Forwarded-Proto` 与 `X-Forwarded-Host`，并限制可信代理来源；Provider、Workbench 和 OAuth 客户端的回调 URI 必须使用同一套公开协议和 Host。

本地 Compose 的 `Development` 配置会生成并持久化开发签名证书，不能作为生产证书。生产密钥、client secret、授权码、token 和完整 Cookie 不得提交或写入普通日志。

## 其他排查

### Token 生成慢

RSA 创建和签名是本地 CPU 操作，不应为了“异步化”包装成 `Task.Run`。应检查重复加载证书、阻塞数据库调用或错误的远程依赖。

### 如何定位请求

优先使用日志中的 TraceId，结合 `docker compose logs` 或 `logs/sso`、`logs/workbench` 排查。日志不得包含密码、client secret、私钥、授权码、access token、refresh token 或完整 Cookie。提问时提供组件、路径、状态码、脱敏错误码和 TraceId，不要上传生产 token、数据库导出或包含 Secret 的配置文件。
