# NexusAuth 使用手册

> 适用版本：当前仓库版本。本文是管理员、应用接入方和运维人员的主入口；协议细节与源码级说明见本文末尾的专题文档。

## 1. 产品与边界

NexusAuth 是基于 .NET 10 的 OAuth 2.0 与 OpenID Connect Provider，包含 Provider、Workbench 管理 API、Workbench Dashboard 和 PostgreSQL 数据库。它提供统一登录、授权、令牌签发、用户管理、客户端管理、服务资源管理与 SCIM 2.0 用户供给。

当前适合机密客户端、Web/BFF、服务间调用和受限设备。浏览器 SPA、移动端与桌面安装包不可安全保存客户端密钥，必须通过 BFF 接入。下列扩展尚未实现：PAR、JAR、JARM、DPoP、mTLS 绑定令牌、动态客户端注册、CIBA 和 `token_endpoint_auth_method=none`。

| 服务 | 默认地址 | 职责 |
|---|---|---|
| Provider | `http://localhost:5100` | 登录、授权、令牌、OIDC、SCIM |
| Workbench API | `http://localhost:5051` | 管理台 BFF 与管理 API |
| Workbench Dashboard | `http://localhost:5273` | 管理界面 |
| PostgreSQL | `localhost:5432` | 业务数据 |

## 2. 快速启动

### 2.1 前置条件

- Docker Engine 与 Docker Compose；或 .NET 10、Node.js 20+、npm 与 PostgreSQL 16。
- 本地端口 `5100`、`5051`、`5273`、`5432` 未被占用。
- 生产环境使用 HTTPS、受控的 Secret 管理与签名证书，不使用下述本地默认值。

### 2.2 Compose 开发环境

在仓库根目录执行：

```bash
docker compose up --build
```

首次启动会创建空数据库的最终 schema、登记 Workbench 系统客户端，并按环境变量创建初始管理员。访问 `http://localhost:5273`，用 Compose 开发回退账号登录：用户名 `admin`，密码 `wzw0126..`。

默认账号和默认 Workbench 密钥仅用于本机开发，绝不能用于生产。停止服务保留数据卷：

```bash
docker compose down
```

仅在确认本地数据可以丢弃时重置数据库：

```bash
docker compose down -v
docker compose up --build
```

### 2.3 本地进程启动

先按 [03 数据库配置](./03-数据库配置.md) 准备数据库和 schema，再分别运行：

```bash
dotnet run --project src/NexusAuth.Host
dotnet run --project admin/src/NexusAuth.Workbench.Api
cd admin/src/NexusAuth.Workbench.Dashboard
npm install
npm run dev
```

本地进程方式不会自动提供生产管理员或 Workbench 密钥；请在运行环境中配置第 8 节的变量。

## 3. 首次管理员与登录

初始管理员由 Provider 的 `BootstrapAdmin` 配置创建，而不是 SQL 固定账号。以下变量必须成对设置用户名和密码：

```bash
NEXUSAUTH_BOOTSTRAP_ADMIN_USERNAME=admin
NEXUSAUTH_BOOTSTRAP_ADMIN_PASSWORD=REPLACE_WITH_A_STRONG_PASSWORD
NEXUSAUTH_BOOTSTRAP_ADMIN_NICKNAME="System Admin"
NEXUSAUTH_BOOTSTRAP_ADMIN_EMAIL=admin@example.com
```

启动逻辑具有幂等性：不存在该用户名时创建并标记为系统账户；已存在时保留其密码，并确保其为系统账户。系统账户不能通过管理功能修改或删除，应使用受控的启动配置和数据库恢复流程管理。

登录 Dashboard 后，浏览器只持有 Workbench BFF 的受保护 Cookie；OAuth 客户端密钥、access token 与 refresh token 不应放进浏览器存储或前端构建产物。

Provider 登录页的“3 天内免登录”复选框由 `NEXUSAUTH_LOGIN_FLOW_REMEMBER_ME_LIFETIME_DAYS` 配置。未设置时为 3 天，可设置 1–30 天；例如 `NEXUSAUTH_LOGIN_FLOW_REMEMBER_ME_LIFETIME_DAYS=7`。勾选后，持久 Cookie 与服务端 SSO 会话在固定期限后同时失效，不会因持续访问而续期；修改变量后重启 Provider。

## 4. 管理台操作

管理台分为用户、服务资源、应用管理和 SCIM 凭证。资源的名称、客户端 ID、回调地址和凭据是安全边界，修改前先确认依赖它们的应用。

### 4.1 用户管理

在“用户管理”中查询用户、编辑展示资料、启用或禁用账号、重置密码。管理界面使用用户名、昵称、邮箱、电话、状态和 SCIM 资料字段作为业务信息；内部用户 ID 仅用于接口和审计关联，不作为日常管理对象。

- 禁用用户会阻止后续登录；恢复后才能继续认证。
- 重置密码后应通知用户通过安全渠道设置新密码。
- 系统账户不可编辑、禁用、重置密码或删除。
- SCIM 供给的用户可同时在此查看；跨系统主键使用 `externalId`，不要把本地 UUID 当作外部身份源 ID。

### 4.2 服务资源与 Scope

服务资源代表可被 access token 授权的 API。创建时填写：

| 字段 | 规则 |
|---|---|
| `name` | Scope 名称，整个系统唯一，例如 `orders.read`；创建后不能改名。 |
| `displayName` | 管理台展示名。 |
| `audience` | access token 的目标受众，例如 `orders-api`。 |
| `description` | 可选业务说明。 |
| 状态 | 禁用后不应再向新授权签发该 Scope。 |

系统标准 Scope 包括：`openid`、`profile`、`email`、`phone`、`address`、`offline_access`。其中 `openid` 用于 OIDC，`profile` 等用于用户声明，`offline_access` 用于申请 refresh token；它们不需要重复建成普通服务资源。业务 API Scope 则通过服务资源创建。

删除服务资源前，先从所有客户端解除关联；删除会影响新授权请求的 Scope 校验。名称不可重复，不能用“同名不同 audience”规避唯一性。

### 4.3 应用（OAuth 客户端）管理

创建应用时配置以下内容：

| 配置 | 建议与约束 |
|---|---|
| `client_id` | 系统唯一且稳定，例如 `orders-bff`；创建后不改。 |
| 回调地址 | `redirect_uri` 与 `post_logout_redirect_uri` 精确匹配，包含协议、域名、端口、路径和大小写。 |
| 授权类型 | 按实际流程选择 `authorization_code`、`refresh_token`、`client_credentials` 或 `device_code`。 |
| PKCE | Web/BFF 推荐开启，只接受 `S256`。 |
| 客户端认证 | 一次选择一种：`client_secret_basic`、`client_secret_post`、`client_secret_jwt` 或 `private_key_jwt`。 |
| 标准 Scope | 从标准 Scope 选择，例如 `openid profile offline_access`。 |
| 服务资源 | 多选已启用的业务资源。后端会把标准 Scope 与服务资源名称统一累加、去重后写入客户端 `AllowedScopes`。 |

推荐 BFF 配置：`authorization_code` + `refresh_token`、`require_pkce=true`、`client_secret_basic`，Scope 使用 `openid profile offline_access YOUR_API_SCOPE`。纯服务调用使用 `client_credentials`，不要申请 `openid` 或用户资料 Scope。

生成或重置凭据后，明文 `client_secret` 或私钥只显示一次。立即写入 Vault、Kubernetes Secret 或受控 Secret 管理器；不要放进 Git、前端环境变量、日志或工单。重置会使旧共享密钥失效，务必先完成依赖应用的密钥更新并安排回滚方案。

### 4.4 管理 API

Dashboard 使用以下经 OIDC 登录保护的 API。所有接口的 `id` 都是内部 UUID；日常运维优先使用 Dashboard，接口适合自动化和排障。

| 对象 | API |
|---|---|
| 当前登录、登录、登出 | `GET /api/auth/me`、`GET /api/auth/login`、`POST /api/auth/logout` |
| 用户 | `GET /api/users`、`GET/PUT /api/users/{id}`、`PATCH /api/users/{id}/status`、`POST /api/users/{id}/reset-password` |
| OAuth 客户端 | `GET/POST /api/clients`、`PUT/DELETE /api/clients/{id}`、`POST /api/clients/{id}/credentials`、`POST /api/clients/{id}/credentials/reset` |
| 服务资源 | `GET/POST /api/api-resources`、`PUT/DELETE /api/api-resources/{id}`、`PATCH /api/api-resources/{id}/status` |
| 客户端元数据 | `GET /api/client-metadata` |
| SCIM 凭证 | `GET/POST /api/scim-credentials`、`PUT /api/scim-credentials/{id}`、`POST /api/scim-credentials/{id}/revoke` |

## 5. OAuth 2.0 与 OIDC 接入

接入方先读取发现文档，而不是硬编码端点：

```bash
curl http://localhost:5100/.well-known/openid-configuration
```

当前主要端点：`/connect/authorize`、`/connect/token`、`/connect/userinfo`、`/connect/endsession`、`/connect/deviceauthorization`、`/connect/introspect`、`/connect/revocation` 和 `/.well-known/jwks.json`。

### 5.1 授权码 + PKCE

1. 在管理台登记机密 BFF 客户端，启用 `authorization_code` 与 PKCE。
2. 每次登录生成随机 `state`、OIDC `nonce`、43 至 128 字符的 `code_verifier`，计算 Base64Url(SHA-256(verifier)) 为 `code_challenge`。
3. 浏览器跳转 `/connect/authorize`；回调地址必须与登记值精确一致。
4. BFF 校验回调的 `state`，然后由服务端调用 `/connect/token` 兑换授权码。
5. BFF 把令牌存进受保护的服务端会话或 HttpOnly Cookie；React 等前端只调用 BFF。

示例授权请求：

```text
http://localhost:5100/connect/authorize?response_type=code&client_id=orders-bff&redirect_uri=https%3A%2F%2Fapp.example.com%2Fsignin-oidc&scope=openid%20profile%20offline_access%20orders.read&state=RANDOM_STATE&nonce=RANDOM_NONCE&code_challenge=S256_CHALLENGE&code_challenge_method=S256
```

使用 `client_secret_basic` 兑换：

```bash
curl -i -X POST http://localhost:5100/connect/token \
  -u 'orders-bff:REPLACE_WITH_CLIENT_SECRET' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'grant_type=authorization_code' \
  --data-urlencode 'client_id=orders-bff' \
  --data-urlencode 'code=REPLACE_WITH_AUTHORIZATION_CODE' \
  --data-urlencode 'redirect_uri=https://app.example.com/signin-oidc' \
  --data-urlencode 'code_verifier=ORIGINAL_VERIFIER'
```

`response_mode` 支持 `query` 和 `form_post`。只有客户端和 `redirect_uri` 都已安全验证时，Provider 才会把错误与原始 `state` 回传；否则直接在 Provider 返回本地错误页面。

### 5.2 服务间调用

将客户端授权类型设为 `client_credentials`，只配置业务 API Scope。用注册的认证方式请求 token，例如：

```bash
curl -X POST http://localhost:5100/connect/token \
  -u 'inventory-worker:REPLACE_WITH_CLIENT_SECRET' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'grant_type=client_credentials' \
  --data-urlencode 'scope=inventory.read'
```

这类 token 不代表终端用户。资源服务器必须验证签名、`iss`、有效期、`aud` 与所需 Scope。

### 5.3 Refresh、登出与撤销

只有客户端允许 `refresh_token` 且授权请求包含 `offline_access` 时，响应才含 refresh token。刷新会轮换旧 token，客户端必须原子地替换保存值；旧 token 被并发重用会失败。用户登出使用 `/connect/endsession`；撤销使用 `/connect/revocation`。令牌内容永远不能进入日志。

客户端认证来源不能混用。Basic、表单密钥、共享密钥 JWT 断言和私钥 JWT 断言出现冲突时返回 `invalid_client`（HTTP 401 与 `WWW-Authenticate`）。详细请求样例见 [05 配置 OAuth 客户端](./05-配置OAuth客户端.md)。

## 6. SCIM 2.0 用户供给

SCIM 基址为 `https://sso.example.com/scim/v2`。它使用专用 Bearer Token，不使用用户 access token。凭证在 Workbench 的“SCIM 凭证”中创建，创建响应中的 Token 只返回一次；保存后只能撤销并重新生成。

为每个身份源单独创建凭证，按最小权限授予：

| Scope | 权限 |
|---|---|
| `scim:read` | 读取 ServiceProviderConfig、Schema、ResourceType 与用户。 |
| `scim:write` | 新建、替换、PATCH、删除用户；读取操作也应同时授予 `scim:read`。 |

支持端点为 `GET /ServiceProviderConfig`、`/ResourceTypes`、`/Schemas`、`GET/POST /Users`、`GET/PUT/PATCH/DELETE /Users/{id}`。请求和响应使用 `application/scim+json`，并支持 `If-Match` ETag 并发控制。用户的外部主键应写入 `externalId`；`userName` 必填且系统唯一。

创建用户示例：

```bash
curl -X POST https://sso.example.com/scim/v2/Users \
  -H 'Authorization: Bearer REPLACE_WITH_SCIM_TOKEN' \
  -H 'Content-Type: application/scim+json' \
  --data '{"schemas":["urn:ietf:params:scim:schemas:core:2.0:User"],"userName":"alice","externalId":"idp-1001","active":true,"name":{"givenName":"Alice","familyName":"Zhang"},"emails":[{"value":"alice@example.com","primary":true}]}'
```

当前实现的限制：仅 User 资源；不支持 SCIM Bulk、排序与 Change Password；`emails` 和 `phoneNumbers` 每类仅接受一个主值；过滤能力以服务返回的 `ServiceProviderConfig` 为准。若 IdP 支持禁用优于删除，建议优先 PATCH `active=false`，保留审计与账号恢复能力。

## 7. 生产上线清单

1. 设置公网 HTTPS `NEXUSAUTH_JWT_ISSUER`，并确保 Provider、发现文档、客户端回调和反向代理一致。
2. 显式配置初始管理员变量与 `WORKBENCH_CLIENT_SECRET`，不使用 Compose 回退值。
3. 提供受管 X.509 PFX：设置 `NEXUSAUTH_SSO_ENVIRONMENT=Production`、`NEXUSAUTH_JWT_SIGNING_MODE=Certificate`、`NEXUSAUTH_JWT_SIGNING_CERTIFICATE_PATH` 与密码 Secret。生产不会自动生成签名证书。
4. 为 Provider 与 Workbench 多副本共享 Data Protection key ring，并持久化 PostgreSQL。
5. 使用空库时执行 [production-init.sql](../production-init.sql)。当前部署模型要求从全新数据库初始化，不提供历史库的增量升级脚本。
6. 确认数据库账号可使用 `pgcrypto`。若受管 PostgreSQL 禁止 `CREATE EXTENSION`，由 DBA 预先启用扩展。
7. 将 `WORKBENCH_CLIENT_SECRET` 与完整的 `NEXUSAUTH_WORKBENCH_AUTH_*`、`NEXUSAUTH_WORKBENCH_BOOTSTRAP_*` 配置提供给 Workbench API。系统会在 API 启动时创建或同步内置客户端、resource 和密钥；密钥变更后滚动重启 Workbench 即可。
8. 配置可信转发头、明确 `AllowedHosts`、HTTPS Cookie、日志保留、监控、备份与恢复演练。
9. 不在生产执行 `demo/seed.sql`，不提交真实 Secret、PFX、私钥、token 或生产数据库导出。

## 8. 配置参考

| 变量 | 说明 |
|---|---|
| `ConnectionStrings__Default` | Provider 与 Workbench API 的 PostgreSQL 连接串。 |
| `NEXUSAUTH_JWT_ISSUER` / `Jwt__Issuer` | 对外 Provider 地址，生产必须为 HTTPS。 |
| `NEXUSAUTH_BOOTSTRAP_ADMIN_*` | 初始系统管理员资料。 |
| `WORKBENCH_CLIENT_SECRET` | Workbench OAuth 客户端唯一密钥来源，由 API 启动初始化器同步。 |
| `NEXUSAUTH_SSO_ENVIRONMENT` | 生产设为 `Production`。 |
| `NEXUSAUTH_JWT_SIGNING_MODE` | 新部署推荐 `Certificate`。 |
| `NEXUSAUTH_JWT_SIGNING_CERTIFICATE_PATH` / `...PASSWORD` | 生产 PFX 路径和密码。 |
| `NEXUSAUTH_ACCESS_TOKEN_LIFETIME_MINUTES` | access token 生命周期，默认 60 分钟。 |
| `NEXUSAUTH_REFRESH_TOKEN_LIFETIME_MINUTES` | refresh token 绝对生命周期，默认 43200 分钟。 |
| `NEXUSAUTH_LOGIN_FLOW_REMEMBER_ME_LIFETIME_DAYS` | 登录页“几天内免登录”的固定有效期，默认 3 天，允许 1–30 天；Cookie 与服务端 SSO 会话同时到期且不滑动续期。 |

## 9. 常见故障

| 现象 | 优先检查 |
|---|---|
| `invalid_client` | 客户端状态、认证方式、密钥是否轮换、Basic/表单/JWT 认证是否混用；Workbench 还检查 `WORKBENCH_CLIENT_SECRET`。 |
| `redirect_uri` 错误 | 请求值是否与登记值逐字符一致，包含末尾 `/`、端口和大小写。 |
| `invalid_scope` | Scope 是否在客户端授权范围内，服务资源是否启用，标准 Scope 与服务资源名称是否正确。 |
| `invalid_grant` | 授权码是否重复使用或过期、回调地址与 PKCE verifier 是否匹配。 |
| 登录后循环跳转 | Workbench 的 Authority、回调地址、Cookie/Data Protection 和反向代理 HTTPS 头是否一致。 |
| 免登录期限不符合预期 | 检查 `NEXUSAUTH_LOGIN_FLOW_REMEMBER_ME_LIFETIME_DAYS` 是否为 1–30 的整数，且 Provider 已重启；已签发 Cookie 不会被新配置延长。 |
| SCIM 401/403 | Bearer Token 是否有效、未撤销或过期；读取授予 `scim:read`，写入授予 `scim:write`。 |
| Provider 启动失败 | 数据库连通性、schema、签名证书路径/密码及生产环境变量。 |

日志可通过 `docker compose logs` 或 `logs/sso`、`logs/workbench` 查看。排障可使用 TraceId 关联请求，但不得把密码、client secret、私钥、授权码、access token、refresh token 或完整 Cookie 写入日志。
